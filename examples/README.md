# RedirectHunter Examples

Sample input files and configuration, one per supported input format, plus a
sample YAML config. Every file here is verified against the real loader and
config-resolution code (see `tests/test_loader.py` and `tests/test_config.py`)
— nothing in this directory is illustrative-only.

## Input files

| File | Format | Notes |
|---|---|---|
| `urls.txt` | TXT | One URL per line; `#` comments and blank lines are skipped. |
| `urls.csv` | CSV | Header row (`url,campaign,owner`); extra columns become `row_metadata`. |
| `urls.json` | JSON | Mix of object entries (with metadata) and a plain string entry. |
| `urls.db` | SQLite | Generated by `create_sample_sqlite.py`; table `urls`, column `url`. |
| `backlink-sample.txt` | TXT | Generic `bl-check` input: plain URL, `\|target` override, `account_id\|URL` rows. |
| `bl-check-accounts.txt` | TXT | `--accounts-file` registry template, pairs with `backlink-sample.txt`'s account rows. |
| `bl-chain-tier1.txt` / `tier2.txt` / `tier3.txt` | TXT | Dummy three-tier link pyramid for `redirecthunter bl-chain`. |

All four contain the same underlying candidate URLs (with `{TARGET}`
placeholders) so you can compare formats directly:

```bash
redirecthunter scan examples/urls.txt  --target https://example.org
redirecthunter scan examples/urls.csv  --target https://example.org
redirecthunter scan examples/urls.json --target https://example.org
redirecthunter scan examples/urls.db   --target https://example.org
```

### Regenerating `urls.db`

`urls.db` is a small generated SQLite file, not hand-authored. Regenerate it
with:

```bash
python3 examples/create_sample_sqlite.py
```

### Custom SQLite table/column names

If your own SQLite input doesn't use the `urls` table / `url` column
defaults, point RedirectHunter at the right ones:

```bash
redirecthunter scan mydata.db --input-table candidates --input-column target_url
```

## Backlink verification sample

`backlink.txt` is a one-URL-per-line input for `redirecthunter bl-check`
(see the main [README](../README.md#backlink-verification-redirecthunter-bl-check)).
It's a real, mixed set: server-rendered pages the default (httpx) mode
handles directly, plus JS SPA profiles (YouTube, Disqus, X, Instagram,
Threads) and anti-bot-protected pages (LinkedIn, Facebook) that need
`--browser` and, in LinkedIn/Facebook's case, still won't fully resolve
either way — good for seeing the full range of outcomes in one run.
Note this file is one project user's own real data, kept here as an
internal reference for that range of outcomes -- it's not a generic
format example; use [`backlink-sample.txt`](backlink-sample.txt) below
for that instead.

```bash
redirecthunter bl-check examples/backlink.txt -d medilana.id
```

The last line demonstrates the per-row target override: appending
`|target` to a URL pins that row to a specific target instead of the
run's `-d/--domain`, and a `;`-separated list
(`|medilana.co.id;form.medilana.com;img.medilana.my.id`) pins it to
*several* acceptable targets at once — the row matches if the page
links to any one of them. See
[`docs/CLI_REFERENCE.md`](../docs/CLI_REFERENCE.md#bl-check) for the
full syntax, including how blank/whitespace-only entries are handled.

### Reusable header/cookie sets for login-walled pages

Some URLs in a backlink list only show their real content to a logged-in
session (LinkedIn, Facebook, vendor-marketplace profile/group pages, etc).
`bl-check`'s `-H`/`--header` accepts a domain-scoped cookie
(`-H "linkedin.com|Cookie: li_at=..."`) so it's sent only to that platform,
never leaked to the rest of the (usually much larger) URL list.

Instead of retyping `-H` on every run, put the same lines in a file and pass
`--headers-file`:

```bash
redirecthunter bl-check backlinks.txt -d medilana.id --headers-file my-headers.txt
```

See [`examples/bl-check-headers.txt`](bl-check-headers.txt) for the exact
file format and, importantly, **how to copy the right cookie value** --
copy the literal `Cookie:` request header from DevTools' *Network* tab
(not individual cookie names from the Application/Storage panel, which
mixes your session cookie in with unrelated analytics/ad cookies you can't
tell apart by name alone). Keep your filled-in copy out of version control;
it holds real session credentials.

For an even faster path than DevTools, the bundled
[`rh-cookie-copier/`](../rh-cookie-copier) browser extension does this in
one click: open the logged-in site, click the extension icon, and a
ready-to-paste `domain|Cookie: ...` line lands on your clipboard. Works on
Chrome, Edge, Brave, Opera, and Firefox -- see `rh-cookie-copier/README.md`
for the (under-a-minute) local install steps.

### Account-scoped sessions (`--accounts-file`)

`-H`/`--headers-file` above cover one session per whole run (or per
platform domain). That's not enough when the *same* domain needs
**several** different sessions at once -- e.g. auditing placements
posted from 30 different accounts on the same platform, where each
placement's row needs its own Cookie. `--accounts-file` is for that
case: a registry of `account_id -> headers`, paired with input rows
prefixed `account_id|URL` (or an `account_id` column/key for CSV/JSON).

```bash
redirecthunter bl-check examples/backlink-sample.txt -d medilana.id \
  --accounts-file examples/bl-check-accounts.txt
```

(This exact command will exit with a "missing account_id" error until
you fill in and uncomment real `account_001`/`account_002` entries in
your own copy of `bl-check-accounts.txt` -- the shipped example file has
every account commented out, on purpose, so it never holds real
credentials.)

[`examples/backlink-sample.txt`](backlink-sample.txt) is a generic,
dummy input showing all three row shapes at once: a plain public URL, a
URL with its own `|target` override, and `account_id|URL` rows
(including the same account reused across rows, and two different
accounts on the same platform domain).
[`examples/bl-check-accounts.txt`](bl-check-accounts.txt) is the
matching registry template -- same cookie-copying guidance as
`bl-check-headers.txt` above, just keyed by `account_id` instead of
domain. A row referencing an `account_id` that isn't in the registry is
a hard error (exit code 1, listing every missing `account_id`) --
`bl-check`/`bl-chain` never silently fall back to an anonymous request.
See
[`docs/BACKLINK_GUIDE.md#account-scoped-sessions-accounts-file`](../docs/BACKLINK_GUIDE.md#account-scoped-sessions-accounts-file)
for the full syntax and behavior.

### Chained/tiered example

[`examples/bl-chain-tier1.txt`](bl-chain-tier1.txt),
[`examples/bl-chain-tier2.txt`](bl-chain-tier2.txt), and
[`examples/bl-chain-tier3.txt`](bl-chain-tier3.txt) are a dummy
three-tier link pyramid for `redirecthunter bl-chain` -- tier 1 pages
that should link to the root domain, tier 2 pages that should link to a
tier-1 host, tier 3 pages that should link to a tier-2 host. Tier 1
also includes one `account_id|URL` row, showing `--accounts-file` works
across tiers (one registry, shared by every tier) the same way it does
for a plain `bl-check` run:

```bash
redirecthunter bl-chain examples/bl-chain-tier1.txt examples/bl-chain-tier2.txt examples/bl-chain-tier3.txt \
  -d medilana.id --accounts-file examples/bl-check-accounts.txt
```

(Same caveat as above: `bl-check-accounts.txt` ships with every account
commented out, so this needs a real, uncommented `account_001` entry in
your own copy before it'll actually run instead of erroring on the
missing account reference.)

See
[`docs/BACKLINK_GUIDE.md#chained-tiered-audits-redirecthunter-bl-chain`](../docs/BACKLINK_GUIDE.md#chained-tiered-audits-redirecthunter-bl-chain)
for why tiered audits exist and how each tier's default target set is
derived from the previous tier.

## Sample configuration

`redirecthunter.yaml` demonstrates every configurable field. Use it directly:

```bash
redirecthunter scan examples/urls.txt --config examples/redirecthunter.yaml
```

Or copy it to your project root as `redirecthunter.yaml` for automatic
discovery (no `--config` flag needed):

```bash
cp examples/redirecthunter.yaml ./redirecthunter.yaml
redirecthunter scan examples/urls.txt   # config auto-discovered
```

Remember: CLI flags always override the YAML file, which always overrides
built-in defaults.

## A complete walkthrough

```bash
# 1. Run a scan (GET is required to catch meta-refresh/JS redirects, not just HTTP 3xx)
redirecthunter scan examples/urls.txt --target https://example.org --method GET

# 2. Check aggregate stats (the scan_id is printed at the start of step 1)
redirecthunter stats <scan_id>

# 3. Inspect individual results, filtered to only the redirects found
redirecthunter show <scan_id> --redirects-only

# 4. Export for further analysis
redirecthunter export <scan_id> results.csv
redirecthunter export <scan_id> results.json --format json
```

## Migrating from `url-target-replace.sh`

The old `url-target-replace.sh` Bash+Perl script has been retired. Its two
directions are now first-class, tested CLI commands:

```bash
# domain -> {TARGET} (replaces the old script's default direction)
redirecthunter redact-target urls.txt -d medilana.id -o out.txt

# {TARGET} -> domain (new; previously required a full scan)
redirecthunter expand-target out.txt --target https://medilana.id
```

See [`docs/CLI_REFERENCE.md`](../docs/CLI_REFERENCE.md) for every flag on
both commands, including the short-flag aliases kept for compatibility
with the old script's operator workflow.
